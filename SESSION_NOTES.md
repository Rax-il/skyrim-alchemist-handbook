# Контекст сессии — перенос "Справочника алхимика" на Tauri

Заметки для следующей сессии (Claude или человека) — что уже сделано,
что проверено, что осталось. Проект: Skyrim-алхимический справочник,
переписан с egui/eframe (Rust) на Tauri 2 + React + TypeScript + Vite +
Mantine, поиск сочетаний ингредиентов/свойств, БД — встроенный SQLite
(`rusqlite`, bundled) с картинками в BLOB.

## Хронология этой сессии

1. Изначально был отдельный Rust/egui-проект (`alchemist-rust.zip`),
   который перестал запускаться под Windows после обновления ОС.
   Полностью переписали интерфейс на Tauri+React+Mantine, сохранив всю
   бизнес-логику БД (`db.rs`, `seed_data.rs`, `rare_curios.rs`,
   `creations.rs`) один в один.
2. Пользователь развернул проект локально на Ubuntu 24.04, поставил
   зависимости (`npm install`, Rust уже был), запустил `npm run tauri dev`
   — заработало.
3. Дали 4 замечания по UI, все разобраны и исправлены (см. ниже).
4. Столкнулись с двумя раундами "протухшего состояния", которые маскировали
   применение фиксов — тоже разобрано (см. ниже, важно для будущих сессий).
5. Начали кросс-компиляцию под Windows через `cargo-xwin` — в процессе на
   момент этой заметки (упёрлись в отсутствие `clang-cl`, решается
   симлинком `sudo ln -s /usr/bin/clang /usr/bin/clang-cl`).

## Что исправлено и как (важно для повторного использования кода)

### 1. Картинки не отображались (главный баг)
**Причина**: `paths::database_path()` кладёт БД рядом с exe
(`current_exe().parent()`). В dev-режиме (`npm run tauri dev`) cargo
кладёт бинарник в `src-tauri/target/debug/`, а НЕ в корень проекта, где
лежит готовая `alchemist.db` с картинками. Поэтому там создавалась
**новая пустая** БД без картинок (пути `image_url` в `seed_data.rs` вида
`images/*.png` — исторический артефакт, папки `images/` физически давно
нет, все картинки уже в BLOB в `alchemist.db`).

**Фикс**: `alchemist.db` теперь зашивается в бинарник через
`include_bytes!` (см. `src-tauri/src/paths.rs`, константа `SEED_DB`) и
разворачивается рядом с exe при старте, ЕСЛИ файла там ещё нет
(`ensure_seed_db()`, вызывается в `lib.rs` перед `db::ensure_db`).
Идемпотентно — существующий файл никогда не перезаписывается.

**Побочный эффект / ловушка**: если фикс применить, когда в
`target/debug/` уже лежит СТАРАЯ пустая база (создана до фикса) — фикс
не сработает, т.к. проверяет только "файла ещё нет". Нужно вручную
удалить протухший файл:
```bash
find src-tauri/target -name "alchemist.db" -delete
```
Это один из двух "протухших кэшей", о которые мы спотыкались — держать в
голове на будущее.

### 2-3. Стартовый размер главного окна и окна редактора
Увеличили в `src-tauri/tauri.conf.json`: `900×600` → `1000×800`.
Modal редактора: `size="lg"` → `size="xl"`.

**Ловушка №2**: `tauri-plugin-window-state` сохраняет размер/позицию окна
в файле **вне проекта** — на Linux у пользователя оказалось в
`~/.config/ru.alchemist.app/.window-state.json` (НЕ в `~/.local/share`,
как можно было бы ожидать / как написано в некоторых доках — на разных
системах может отличаться). Этот файл переживает и `git checkout`, и
замену исходников, и маскирует любые изменения `tauri.conf.json`
initial size. При отладке похожих "ничего не поменялось после фикса"
проблем — первым делом ищи:
```bash
find ~/.local/share ~/.config ~/.cache -iname "*window-state*" 2>/dev/null
```
и удаляй.

### 4. Алгоритм адаптации размера картинки по качеству
Перенесли `AlchemistApp::display_size_for` из исходного egui `main.rs`:
контейнер всегда 220×220, картинка внутри рисуется в РЕАЛЬНОМ размере
220 или 100 (не object-fit) в зависимости от того, больше ли 100px хотя
бы одна сторона исходника. Реализовано как хук
`src/lib/useAdaptiveImageSize.ts`, используется в `BottomPane.tsx` и
`EditorModal.tsx`.

### 5. Контраст hover в выпадающих списках (Select) — НЕ РЕШЕНО
Пробовали дважды:
- Глобальный CSS с классом `.mantine-Combobox-option` + разными
  атрибутами (`data-combobox-selected`, `aria-selected`, потом
  `data-combobox-active`) — **не сработало**, подтверждено скриншотами
  пользователя (подсветка остаётся дефолтной бледно-серой).
- Официальный Styles API через `theme.components.Select.extend({styles:
  {option: {'&[data-combobox-active]': {...}}}})` в `main.tsx` — собрали,
  правило видно в JS-бандле (`grep data-combobox-active dist/*.js` находит
  2 вхождения), но **пользователь пока не подтвердил, что это сработало
  визуально** — решили отложить проверку до Windows (гипотеза: возможно,
  дело в Linux/GTK-теме, просачивающейся в WebKitGTK-рендеринг, и на
  Windows/WebView2 будет иначе).

**Если возвращаться к этой проблеме**: текущее состояние —
`main.tsx` содержит `Select.extend()` с `data-combobox-active`,
`index.css` НЕ содержит попыток с классом `.mantine-Combobox-option`
(убрано как мёртвый код). Если и это не сработает на Windows — следующий
шаг: передавать `styles` проп НАПРЯМУЮ в каждый `<Select>` (не через
тему) для проверки, реально ли применяется хоть что-то, либо
попробовать через DevTools посмотреть computed style наведённого
пункта и понять, что именно его перебивает.

### 6. "Выход" в меню не закрывал окно
**Причина**: Tauri v2 требует ОТДЕЛЬНОЕ разрешение
`core:window:allow-close` — `core:default` его не включает. Классическая
ловушка Tauri v2: любое "тихо ничего не происходит" при клике — почти
всегда нехватка permission в `capabilities/default.json`. Если ещё
что-то подобное всплывёт — сразу проверять DevTools Console (там Tauri
прямо пишет название нужного permission) и текущий `capabilities/default.json`.

**Фикс**: добавлено `"core:window:allow-close"` в permissions.

## Сборка под Windows — текущий статус (в процессе на момент записи)

Кросс-компиляция с Linux через `cargo-xwin` (MSVC-таргет, эмулирует
линковщик и сам скачивает Windows SDK — тяжелее и капризнее, чем было
у чистого Rust-бинарника через `x86_64-pc-windows-gnu` в старой
egui-версии).

Пройденные шаги:
```bash
rustup target add x86_64-pc-windows-msvc   # ок
cargo install cargo-xwin                    # ок, ~1m35s компиляции
cargo install tauri-cli --version "^2" --locked  # ок (вывод не смотрели)
npm run build                                # собрать dist/
cd src-tauri
cargo xwin build --release --target x86_64-pc-windows-msvc
```
Споткнулись на отсутствии `clang-cl` (нужен для сборки `rusqlite`
bundled — там компилируется C-код SQLite). На Ubuntu 24.04 `clang-cl`
не создаётся автоматически при `apt install clang` — пришлось руками:
```bash
sudo ln -s /usr/bin/clang /usr/bin/clang-cl
```
На момент этой заметки пользователь повторно запустил
`cargo xwin build --release --target x86_64-pc-windows-msvc` после
симлинка — результат ещё не получен, ждём.

**Если снова спотыкается на сборке C-зависимостей под MSVC-таргетом** —
это известное больное место кросс-сборки Tauri (см. README.md, раздел
"Вариант Б"). Запасной путь — собрать прямо на Windows (`rustup` +
`npm run tauri build`, без всякого `cargo-xwin`), см. README "Вариант А".

Готовый exe (если xwin в итоге соберётся) должен появиться в:
```
src-tauri/target/x86_64-pc-windows-msvc/release/alchemist.exe
```
Не забыть: `alchemist.db` теперь ЗАШИТА в бинарник (см. п.1 выше) — можно
даже не копировать рядом отдельно, развернётся сама при первом запуске.

## 7. "Could not connect to localhost: Connection refused" при запуске готового бинарника
**Симптом**: `npm run tauri dev` и `npm run tauri build` — всё ок. А если
взять исполняемый файл (например, тот, что даёт `cargo build --release`
или `cargo xwin build` для Windows-кросс-сборки — см. раздел про сборку
под Windows выше) и запустить напрямую — белый экран с текстом
"Could not connect to localhost: Connection refused".

**Причина**: `src-tauri/Cargo.toml` не объявлял фичу `custom-protocol` для
крейта `tauri`. `npm run tauri build` подставляет её сам через `tauri-cli`
под капотом — поэтому там всё выглядело исправным, и баг был незаметен.
А `cargo build`/`cargo xwin build` напрямую (в обход tauri-cli) фичу не
подставляют — итоговый бинарник ведёт себя как dev-сборка и пытается
подключиться к `devUrl` (`http://localhost:1420`) вместо того, чтобы взять
собранный фронтенд из `dist/` (`frontendDist` в `tauri.conf.json`).

**Фикс**: добавлено в `src-tauri/Cargo.toml`:
```toml
[features]
default = ["custom-protocol"]
custom-protocol = ["tauri/custom-protocol"]
```
Это стандартный паттерн из официального скаффолда Tauri — `tauri dev`
сам подставляет `--no-default-features`, когда `devUrl` — это URL, так что
hot-reload в dev-режиме продолжает работать как и раньше. А любой прямой
`cargo build`/`cargo xwin build` теперь тоже получает production-поведение
по умолчанию, без необходимости вручную дописывать `--features
custom-protocol` в команду сборки.

**Важно для будущих сессий**: это тот случай, когда `npm run tauri build`
"скрывал" баг, который вылезал только при обходе tauri-cli — держать в
голове при отладке похожих "работает через npm run, не работает напрямую
через cargo" ситуаций.

## 9. Окно "О программе" — итерация 2 (высота +30, кнопка доната)
Пользователь подтвердил первую версию окна (500×200, картинка/текст

Дальше попросил:
1. Увеличить высоту всего окна на 30 (200 → 230), при этом **текстовый

2. Разделить правую половину окна по горизонтали на две части: сверху

**Как сделано в `AboutModal.tsx`**: правая колонка стала
`flexDirection: column` с двумя дочерними блоками:
- `TEXT_AREA_HEIGHT = 200` — тот же текстовый блок, что был раньше,
  один в один, просто вложен в новый `<div>` с фиксированной высотой

- `BUTTON_AREA_HEIGHT = 30` — новый блок под кнопку, по центру

- `ABOUT_HEIGHT = TEXT_AREA_HEIGHT + BUTTON_AREA_HEIGHT` (230) —
  используется и для контейнера, и как реальная высота модалки.
- Левая картинка растягивается на всю высоту (230), т.е. на 30px
  больше, чем раньше — это ожидаемо и визуально нормально

**Кнопка "Автору на Эль"**: сейчас `onClick={onClose}` — просто
закрывает окно, чтобы кнопка не была "мёртвой" полностью, но реального
действия (донат-ссылка/адрес) пока нет — стоит TODO-комментарий прямо

`@tauri-apps/plugin-shell`, показ адреса кошелька в диалоге, что-то
ещё) и оформить это по-настоящему.

**Превью через Visualizer не показывалось**: пытался вывести
натурный HTML-превью с base64-картинкой внутри, дважды не подставил

файл), и в целом рендер с большой base64-строкой (~80-90 КБ) в

просто сразу собирать архив — визуальную проверку сделали по
предыдущему скриншоту приложения. **На будущее**: для таких кейсов
(нужно нужно показать реальную картинку в превью) лучше не гнаться за
пиксель-в-пиксель точностью через base64, а либо показать layout с
цветной заглушкой вместо фото, либо сразу положиться на то, что
пользователь проверит визуально после сборки — как в итоге и
получилось.

Устройство (по итогам нескольких раундов правок в этой сессии):

**Пойманный баг (важно для будущих чекбоксов с локальным state)**: в
обработчике чекбоксов `e.currentTarget.checked` читался ВНУТРИ колбэка
`setState(prev => ...)` — это классическая ловушка React: React выполняет
updater-функцию `setState` уже после того, как `currentTarget` синтетического
события обнулён, так что при клике падал `TypeError: null is not an object
(evaluating 'e.currentTarget.checked')`, что роняло весь React-рендер (пустой
белый экран, "зависшее" окно — без error boundary любое исключение при рендере
роняет всё дерево). Чинится чтением `checked` в обычную переменную ДО вызова
`setState`, а не внутри апдейтера. `TopPane.tsx`-чеклист таким багом не
страдал, потому что там `e.currentTarget.checked` читается синхронно и сразу
передаётся дальше как `boolean`.

### Масштаб интерфейса
- Использован официальный механизм Mantine — `theme.scale` (множитель),
  прокидывается в CSS-переменную `--mantine-scale`; ВСЕ rem-based размеры
  Mantine (`rem()`-конвертер) заворачиваются в
  `calc(Xrem * var(--mantine-scale))` — это подтверждено чтением исходников
  (`node_modules/@mantine/core/esm/core/utils/units-converters/rem.mjs`), а
  не догадкой. Мелкий = ÷1.5, Крупный = ×1.5.
- **Ловушка, чуть не пропущенная**: числовой `size`-проп у `<Modal>` тоже
  идёт через `rem()` (см. `getSize()` в Mantine) — то есть сама модалка
  САМА масштабируется. А наши собственные `style={{width: N}}` внутри
  (ширина колонок, высота контента, футера) — обычные px, масштаб не
  учитывают. При "Мелком" модалка сжималась, а внутренняя вёрстка — нет:
  правая колонка обрезалась, разделитель уезжал от центра, снизу оставалась
  пустая полоса (шрифты сжались, а фиксированная высота — нет). Фикс:
  завернуть все наши px-константы в `SettingsModal.tsx` в тот же
  `calc(Npx * var(--mantine-scale))` (см. функцию `scaled()` там).
- Та же ловушка была и в `.menu-bar-button` (`index.css`, строка меню
  "Файл"/"О программе") — `font-size: 13px` жёстко, без масштаба. Фикс —
  та же формула с `var(--mantine-scale)`.
- **Реальный ресайз окна ОС** при "Применить": `getCurrentWindow().setSize(
  new LogicalSize(...))` от базового 1000×800 (`BASE_WINDOW_WIDTH/HEIGHT` в
  `lib/appTheme.ts`, совпадает с `tauri.conf.json`). Потребовался НОВЫЙ
  permission `core:window:allow-set-size` в `capabilities/default.json` —
  без него тихо ничего не происходит (тот же паттерн Tauri v2, что и с
  "Выход"/`allow-close` в прошлой сессии).
- Высота при уменьшении не должна опускаться ниже порога, при котором часть
  боковой панели становится не видна — добавлен `MIN_WINDOW_HEIGHT = 650`
  (`lib/appTheme.ts`), это ПРИКИДКА, не точная величина — пользователь
  может попросить скорректировать после дальнейшего визуального осмотра.
- **Персистентность масштаба**: раньше `alchemist_settings.json` хранил
  только `side_panel_width`/`split_ratio` (`layout.rs`). Добавлено поле
  `scale`. Важно: `App.tsx` (панели) и `Root` в `main.tsx` (масштаб)
  сохраняют настройки НЕЗАВИСИМО друг от друга — если бы оба слепо писали
  весь `Layout`-объект, один затирал бы поле другого своим устаревшим
  значением. Решение — `layout.rs` больше не экспортирует голый `save()`,
  вместо него `save_panel(width, ratio)` и `save_scale(scale)`, каждая
  сначала читает текущий файл (`load()`), меняет только "свои" поля и
  пишет обратно. Новая Tauri-команда `save_scale`, зарегистрирована в
  `lib.rs`. На старте `Root` загружает масштаб через `api.getLayout()`, но
  **не** ресайзит окно при загрузке (это только по явному "Применить") —
  иначе конфликтовало бы с `tauri-plugin-window-state`, которое само
  восстанавливает физический размер окна между запусками.

## Сессия 2026-08-07 — UX редактирования базы (EditorModal), фикс лагов при печати

### Редизайн "Редактирование базы" — основная задача сессии
Закрывает пункт "проработать UX EditorModal", открытый после инцидента с
"Аронией" (см. выше). Финальная модель:
- **Поле "Название"/строку удалили целиком** — по прямой просьбе
  пользователя переименование существующего компонента через
  свободно редактируемое текстовое поле, привязанное к уже загруженной
  записи, было именно тем механизмом, из-за которого возникла путаница с
  "Аронией" (случайно переписали существующий ингредиент новым). Первая
  попытка — вернуть это поле, но заблокировать его для не-пользовательских
  ингредиентов — пользователь отдельно поправил: "не добавляй компоненты,
  которые я не просил" (см. ниже про фидбек-память). Итог: поля для
  переименования нет вообще, идентичность существующего компонента через
  форму редактирования больше не меняется никаким способом.
- **Новая Rust-команда `is_user_added_component`** (`commands.rs`,
  оборачивает уже существующий `db::component_addon`) — фронтенд узнаёт,
  добавлен ли конкретный компонент пользователем (`Addon::UserAdded`).
- **Права доступа по типу ингредиента**: 4 поля "Свойство" и кнопка
  "Удалить" — `disabled`, если компонент НЕ пользовательский; поля
  "Изображение" и "Описание" — редактируемы всегда, для любого типа. Ровно
  то разделение прав, которое пользователь сформулировал явно.
- **Кнопка "Новый"** возвращена (была убрана раньше в этой же сессии вместе
  со строкой "Название", затем понадобилась снова) — теперь имя нового
  ингредиента вводится ТОЛЬКО через отдельную мини-модалку "Новый
  ингредиент" (с проверкой `componentExists` на дубликат), не через поле,
  привязанное к уже существующей записи. После подтверждения имени строка
  "Ингредиент" в основной форме показывает это имя как заблокированный
  (`disabled`) `TextInput`, а не выпадающий список — сменить его можно
  только повторным нажатием "Новый" (через тот же `requestAction`/
  `pendingAction`, что уже защищает от потери несохранённых изменений).
- **Подтверждение при сохранении правок в НЕ-пользовательском ингредиенте**:
  "Вы уверены, что хотите внести изменения в описание базового
  ингредиента?" — `handleSave` теперь делится на валидацию + сам
  `performSave()`; если `!isNew && !editable`, между ними — диалог
  подтверждения (`confirmBaseEdit`), иначе (пользовательский компонент)

- Мелкие текстовые/визуальные правки по ходу: подпись "Компонент" →
  "Ингредиент"; список ингредиентов при открытии формы сразу показывает
  первый по списку вместо пустого состояния с плейсхолдером "— выбрать или
  ввести новое —" (после удаления/после открытия формы — та же логика);

  "Выбрать файл с изображением"; "Убрать картинку" → "Удалить изображение

### Тормоза при печати в "Описание" — отдельное расследование
Пользователь пожаловался на жуткие лаги при печати в поле "Описание"
(ощущение "как будто сложная задача на каждый символ"). Две гипотезы не
подтвердились (задокументировано в памяти, чтобы не наступать снова):
1. Убрать `recomputeDirty()` из `onChange` (заменить на плоский
   `setDirty(true)`) — не помогло.
2. Замемоизировать `previewSrc` картинки через `useMemo` — тоже не помогло
   (проверили целенаправленно: очистили картинку у ингредиента полностью,
   лаг остался).

Ключевая улика получена от пользователя: поиск в `Select` "Ингредиент"
(178 пунктов, есть и на главном экране, и в этом же окне редактора)
печатается без всяких тормозов, а вот именно текстовые поля — тормозят.
**Настоящая причина**: "Описание" было *контролируемым* React-полем
(`value`/`onChange` в state самого `EditorModal`) — на каждый символ
обновлялся state, что перерисовывало ВЕСЬ `EditorModal` целиком, включая
соседние тяжёлые списки (`Select` "Ингредиент" на 178 пунктов + 4×
"Свойство" на 61 пункт). Поиск внутри `Select` не тормозил, потому что
текст фильтра там живёт во *внутреннем* state самого `Select`, наружу не
всплывает и родителя не перерисовывает.

**Фикс**: поле "Описание" сделано неконтролируемым — текст живёт в DOM
через `ref` (`descriptionRef`), а не в React state; `onChange` только
выставляет лёгкие булевы флаги (`descriptionTouched`, `dirty`); текст
читается из ref один раз, в момент "Сохранить"; `key={loadedName}`
пересоздаёт поле (сбрасывает на `defaultValue`) при переключении на
другой ингредиент. Тот же паттерн (`ref` + `defaultValue` + `key`-сброс
через `newDialogGeneration`) применён и к полю "Название" в модалке
"Новый ингредиент" — по прямой просьбе пользователя, хотя там лагов не
было (маленькая модалка без тяжёлых соседей), для единообразия/
профилактики.

Записано в память (`controlled-textarea-rerender-lag`) — общий урок для
любого будущего текстового поля рядом с большими списками в этом проекте.
