# Многоязыковая поддержка — хранение локализованных данных

Дата: 2026-08-10

## Контекст

Приложение — справочник по алхимии Skyrim, сейчас полностью на русском.
В `SettingsModal.tsx` уже объявлен список из 9 языков (`LANGUAGE_OPTIONS`:
ru/en/fr/de/it/es/pl/ja/zh — все официальные локализации Skyrim Special
Edition, включая китайский, который у Bethesda официально текстовый, без
озвучки), но переключение языка сейчас не функционально — только
визуальный state.

Название/описание интерфейса и общий UI-текст можно перевести обычным
способом. Названия ингредиентов и свойств/эффектов — нет: они должны
совпадать с официальной игровой локализацией, иначе справочник не будет
соответствовать тому, что игрок видит в игре. Источник таких названий —
официальные файлы строк Bethesda (`.STRINGS`/`.DLSTRINGS`/`.ILSTRINGS`),
доступные, например, в сборке "Multiple Languages Strings Unified Central
SSE-AE" на Nexus. Строки в этих файлах адресуются по `StringID`, общему для
всех языков одной и той же игровой записи — значит сопоставление возможно
через уже известный русский текст → его `StringID` → тот же `StringID` в
файле нужного языка.

## Область этого документа

Документ описывает **только хранение** локализованных данных (схему БД и
то, как в неё попадают официальные названия). Он **не** описывает:

- UX редактирования базы при нескольких языках (что показывать, если для
  текущего языка перевода ещё нет, как обозначить в форме редактирования,
  что правки уходят только в текущий язык) — обсуждается отдельно, после
  этого документа.
- Перевод самого интерфейса приложения (кнопки, подписи, документация) —
  обычный текстовый перевод, не требует этого пайплайна.
- Конкретный механизм переключения языка в UI (это следствие миграции ниже,
  но экран/поток переключения не проектируется в этом документе).

## Что не меняется

- `properties.type` (`"Улучшение"`/`"Яд"`) — внутренний код, используемый в
  фильтрации (`TYPE_BENEFIT`/`TYPE_POISON` в `db.rs`), не игровое название.
  Подпись на радиокнопках в `ControlPanel.tsx` — обычный UI-текст,
  переводится как любой другой интерфейсный текст.
- `components.id`, `components.image_url`/`image` (BLOB), `components.addon`,
  `properties.id`, `component_properties` — не зависят от языка, остаются
  как есть.
- Основная поисковая логика (`find_pairs`, `find_max_combinations`,
  `find_combinations` в `db.rs`) уже работает через `id`, не через названия;
  названия используются только при формировании текста результата на
  выходе. Сама алгоритмика поиска почти не меняется.

## Архитектура: идентичность отдельно от локализованного контента

Рассмотренные и отклонённые варианты:

- **Отдельная БД-файл на каждый язык** — отклонено. `image`/`addon`/`id`
  общие для всех языков, а `name`/`description` — нет; правка картинки
  пользователем пришлось бы синхронизировать вручную между 9 файлами.
  Также не даёт естественного способа сказать "у этого языка перевода ещё
  нет".
- **Колонки `name_ru`, `name_en`, ... прямо в `components`/`properties`** —
  рабочий вариант (в проекте уже есть прецедент точечных `ALTER TABLE ADD
  COLUMN` в `db.rs`), но раздувает обе таблицы на 9 колонок под имя и 9 под
  описание, и добавление русских описаний по 9 языкам делает `components`
  тяжёлой. Отклонено в пользу более чистого варианта ниже — разница в
  сложности запросов между вариантами минимальна (JOIN на маленьких
  таблицах против прямого SELECT), а нормализация чище отражает "это одна и
  та же сущность, просто на разных языках".
- **Таблицы переводов, ключ (id сущности, язык)** — выбрано. Ниже.

## Схема БД

Две новые таблицы:

```sql
CREATE TABLE component_translations (
    component_id INTEGER NOT NULL,
    lang         TEXT NOT NULL,
    name         TEXT NOT NULL,
    description  TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (component_id, lang)
);

CREATE TABLE property_translations (
    property_id INTEGER NOT NULL,
    lang        TEXT NOT NULL,
    name        TEXT NOT NULL,
    PRIMARY KEY (property_id, lang)
);
```

`lang` — код языка, тот же, что уже используется в `LANGUAGE_OPTIONS`
(`"ru"`, `"en"`, ...).

Существующие колонки `components.name`, `components.description`,
`properties.name` при миграции переносятся как есть в `lang='ru'` и дальше
считаются легаси (приложение перестаёт их читать напрямую после миграции;
физически не удаляются — SQLite-миграция с удалением колонки требует
пересоздания таблицы, а тут в этом нет необходимости).

Отсутствие строки `(id, lang)` в таблице переводов означает "перевода для
этого языка ещё нет" — это осознанно оставлено как открытый вопрос для
последующего обсуждения UX редактирования, а не решается в этом документе.

Редактирование в текущем языке — это upsert одной строки `(component_id,
current_lang)` в `component_translations`; остальные языки не
затрагиваются. Это ровно то поведение, которое было явно запрошено
("изменения только в базу данных текущего языка").

## Источник данных и пайплайн наполнения

Не отдельный скачиваемый языковой пакет — расширение уже существующего
механизма embedded seed-БД (`paths.rs`, `seed_data.rs`).

1. Офлайн-скрипт (не часть рантайма приложения, разовый инструмент
   разработки) сопоставляет текущие 178 русских названий ингредиентов и 61
   название свойств с `StringID` из `Skyrim_Russian.STRINGS`, затем по тем
   же `StringID` достаёт переводы из остальных 8 официальных языковых
   файлов (`Skyrim_English.STRINGS`, `Skyrim_French.STRINGS`, ...,
   `Skyrim_Chinese.STRINGS`).
2. Результат сохраняется в новый сгенерированный файл (по аналогии с
   `seed_data.rs`, который уже помечен как "автосгенерировано из исходных
   данных"), например `seed_translations.rs` — статические таблицы
   `(component_name_ru, lang) -> (name, description?)` и `(property_name_ru,
   lang) -> name`.
3. Новая функция `migrate_i18n()` в `db.rs`, по образцу уже существующих
   `migrate_media`/`migrate_rare_curios`/`migrate_addon_ids`/
   `migrate_images_to_blob`, при старте приложения создаёт таблицы (если их
   ещё нет) и заполняет их из `seed_translations.rs` — одинаково и для
   чистой установки, и для уже существующей у пользователя `alchemist.db`.

Никакого парсинга `.STRINGS`-файлов или сетевых запросов в рантайме
приложения нет — вся работа с игровыми файлами происходит один раз, офлайн,
при подготовке данных разработчиком.

## Затронутый код (ориентировочно, детали — в плане реализации)

**Решение по итогам обсуждения (2026-08-10):** весь текущий API (и `db.rs`,
~20 функций, и `commands.rs`, 15 команд) идентифицирует ингредиент/свойство
строкой-названием (прямое наследие `db.go` из Go-версии — при одном языке
имя и так было уникальным ключом). При переходе на мультиязычность имя
перестаёт быть языково-независимым идентификатором, так что вместо двойного
ключа `(name, lang)` везде — переходим на `component_id`/`property_id`
(`i64`) как основную идентификацию во всех функциях/командах, которые сейчас
принимают `name: &str`/`name: String`. `name`+`lang` используется только
там, где реально нужен текст: при первом резолве введённого/выбранного в UI
названия в `id` (например, поиск в `Select`) и на пути чтения для перевода
результата обратно в текст текущего языка.

Практически это значит:
- `db.rs`: функции вида `component_properties(name)`, `component_exists(name)`,
  `insert_component(name, props)`, `rename_component(old_name, new_name)`,
  `set_component_media(name, ...)`, `update_component_properties(name,
  props)` и т.д. меняют сигнатуру на `id: i64` (и `prop_names: &[String; 4]`
  → `prop_ids: [i64; 4]`); новая функция резолва `(name, lang) → id` нужна
  там, где id ещё не известен (например, при сохранении новой связи
  ингредиент-свойство, когда фронтенд прислал название). `rename_component`
  в старом виде (переименование существующей записи) по итогам сессии
  2026-08-07 уже не используется для существующих компонентов из UI (см.
  SESSION_NOTES.md, раздел "UX редактирования базы") — его дальнейшая судьба
  уточняется в плане реализации.
- Новая `migrate_i18n()` — по аналогии с уже существующими `migrate_*` в
  `db.rs`; "текущий язык" передаётся явно как параметр функций, не читается
  из глобального state (как и раньше — `db.rs` остаётся Tauri-agnostic).
- `commands.rs`: те же команды переходят на `id`; читающие данные для
  отображения дополнительно принимают `lang: String`. Текущий язык хранится
  и передаётся так же, как уже хранятся `scale`/`enabled_addons`/
  `max_combinations` — persisted-поле в `Layout` (`layout.rs`,
  `save_language`/аналог `save_scale`), значение живёт в state `App.tsx` и
  передаётся явным параметром в `invoke()`.
- Фронтенд: `App.tsx` (и всё, что от него зависит — выбор ингредиентов,
  `EditorModal.tsx`) сейчас хранит состояние выбора как строки-названия;
  переходит на числовые `id`, отображаемое название — производное значение
  (резолвится через `lang` для рендера), а не сам ключ состояния.
- `seed_data.rs` / новый `seed_translations.rs`: генерируются офлайн-скриптом,
  в репозитории лежит только результат.

## Открытые вопросы (сознательно не решены в этом документе)

- Поведение UI при отсутствии перевода для текущего языка у
  пользовательского ингредиента (показывать на языке создания с пометкой?
  скрывать? предлагать перевести?) — обсуждается отдельно, следующим шагом,
  вместе с остальным UX редактирования базы при нескольких языках.
- Судьба легаси-колонок `components.name`/`description`/`properties.name`
  после того, как приложение перестанет их читать (оставить навсегда как
  архив/бэкап или отдельной задачей вычистить).

## Дополнение (2026-08-10): реализация плана B, шаг B1 — схема и миграция

По итогам плана A (`docs/superpowers/plans/2026-08-10-i18n-strings-pipeline.md`,
смержен в `master`) реализация разбита на 4 последовательных шага (B1-B4), у
каждого свой цикл spec→plan→код. Это дополнение фиксирует решения для **B1**
(только схема БД + миграция, без изменения поведения приложения).

**Код языка для китайского — `zh-Hant`, не `zh`.** Финальное ревью плана A
отметило, что скачанный файл — это Традиционный китайский, а не обобщённый
"китайский". Значение в `SettingsModal.LANGUAGE_OPTIONS` меняется на
`zh-Hant` в рамках B1 (просто как значение статичного списка — само
переключение языка ещё не работает, это B3), чтобы код языка не разъезжался
между БД и фронтендом уже сейчас.

**Подготовка `seed_translations.rs`:** пайплайн `tools/i18n` (с учётом всех
фиксов из финального ревью плана A — снятие неоднозначных `StringID` через
`OVERRIDES`, обрезка пробелов и т.д.) прогоняется ещё раз против уже
скачанных файлов в `~/Рабочий стол/alchemist-tauri-strings-src/`, на этот раз
с кодом `zh-Hant` вместо `zh` (потребует точечной правки `LANG_SUFFIX` в
`match_translations.py`, чтобы принимать `zh-Hant` как ключ языка). Результат
копируется в `src-tauri/src/seed_translations.rs` и коммитится как обычный
файл с данными — по той же схеме, что и `seed_data.rs` ("автосгенерировано",
не пересобирается при `cargo build`).

**`migrate_i18n()` (`db.rs`, по образцу уже существующих `migrate_*`):**
1. Создаёт `component_translations`/`property_translations`, если их ещё
   нет.
2. Бэкфилл `lang='ru'`: для каждого компонента/свойства без строки перевода
   с `lang='ru'` — вставляет её из **текущего** содержимого
   `components.name`/`description`/`properties.name` (то есть уже с учётом
   правок пользователя, а не из эталонных seed-данных).
3. Заполнение остальных 8 языков из `TRANSLATIONS`
   (`src-tauri/src/seed_translations.rs`): для каждой тройки `(ru_name, lang,
   text)` ищет `id` сначала среди `components.name`, затем среди
   `properties.name` (пересечений между двумя множествами имён нет —
   проверено), и вставляет перевод, если строки для `(id, lang)` ещё нет.
   Имя без соответствия в текущей БД (например "Смертная плоть" — плагин
   Plague of the Dead отсутствует в скачанном архиве) пропускается без
   падения, как и в остальных `migrate_*`.

**Тесты:** по образцу `db::rare_curios_tests` — свежая БД → `migrate_i18n()`
→ таблицы существуют и заполнены (точечная проверка известного имени на
известном языке) → повторный вызов не дублирует строки (идемпотентность).

**Явно вне рамок B1:** ни одна существующая функция `db.rs`/`commands.rs` не
меняет поведение и не читает новые таблицы — приложение продолжает работать
ровно как сейчас, на старых колонках. Переход на чтение из таблиц переводов
и на `id`-идентификацию — это B2 (уже описано выше, в разделе "Затронутый
код").
